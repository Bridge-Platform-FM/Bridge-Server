## What changed

### Feature Changes
This PR is meant to add a "Matching Engine Dashboard" for admins (stats like acceptance rate, engagement, match volume, sector mix, algorithm mix) plus a new endpoint for the frontend to log match interaction events (shown/skipped/flagged/etc.). It's bundled with a large, unrelated migration of primary/foreign key IDs from integers to UUIDs across almost every model, an ESLint rule change, and a rework of auth-cookie handling.

### User-facing impact
- Admin dashboard: a new `GET /api/v1/admin/matching-engine/stats` endpoint intended to power KPI widgets.
- Frontend "explore" page: a new fire-and-forget `POST /api/v1/matching/events` intended to log match interactions — **but as shipped this endpoint is not reachable** (see Impact Analysis), so nothing will actually log.
- Company registration flow (`POST /api/v1/auth/company-registration`): as written, this endpoint will throw at runtime (undefined variables), turning every registration attempt into a 500.
- Every ID (`user.id`, `company.id`, foreign keys) moves from integer to UUID — this changes the shape of every response containing an ID, and breaks any existing stored/bookmarked numeric IDs.

### Risks associated
- **The server will not start.** Duplicate `const` declarations in `src/app.js`, `src/controllers/authController.js`, and `src/controllers/adminController.js` are fatal `SyntaxError`s in JS — this isn't a subtle bug, `node` will refuse to parse these files. This PR cannot be merged/deployed in its current state.
- Scope creep: a dashboard/analytics feature is bundled with a full INTEGER→UUID primary key migration across ~20 models. These are unrelated changes and should not ship in the same PR — the UUID migration alone is a major, high-risk, cross-team change (every downstream integration, cached ID, and the Next.js frontend must handle UUID strings instead of numbers).
- Migrations are gitignored in this repo, so the actual SQL migration for the UUID change (altering column types on tables with existing data and foreign keys) is not in this diff — reviewers cannot verify it's even possible to do safely on non-empty tables.
- Duplicated route registration (`GET /matching-engine/stats` registered twice in `adminRoutes.js`) suggests this diff was assembled from a bad merge/rebase, not manually reviewed before opening the PR.

### Decisions needed
- Should the UUID migration be split into its own PR with its own review and migration/rollback plan, separate from the matching dashboard feature? (Recommended: yes.)
- Is there a maintenance window / migration plan for converting existing production integer IDs to UUIDs without breaking the live Next.js frontend and any external integrations that store numeric user/company IDs?
- Product sign-off needed: `companyRegistration` now appears to set long-lived auth cookies before OTP/MFA verification completes (see Security issues) — was pre-MFA authentication intended, or is this a bug?
